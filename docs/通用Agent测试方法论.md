# 通用 Agent 测试方法论

## 1. 文档目的

这套方法用于验证一个 Agent 是否不仅能完成基本演示，还能在边界情况、异常情况和依赖失败时稳定、诚实、可追踪地工作。

它适用于带有知识库、RAG、记忆、外部搜索、数据库或其他工具调用能力的 Agent，也适用于更简单的对话型 Agent。

核心思想是：

```text
明确目标 → 梳理流程 → 设计测试 → 定义标准 → 自动执行 → 分析修复 → 回归测试 → 发布监控
```

## 2. 明确 Agent 的目标和功能

测试开始前，先回答三个问题：

1. Agent 要帮助用户解决什么问题？
2. Agent 需要具备哪些功能类别？
3. Agent 明确不能做什么？

功能类别应按用户目标划分，而不是按代码模块划分。例如，一个 Agent 可能需要：

- 根据用户数据进行推荐；
- 从知识库中检索信息；
- 查询实时外部信息；
- 读取或保存用户记忆；
- 处理不完整、错误或超出范围的问题；
- 对无法完成的请求进行解释和降级。

每一类功能都应该有清晰的成功定义。成功不只是“返回了文字”，而是“完成了正确的任务，并且没有虚构、越权或遗漏关键条件”。

## 3. 梳理 Agent 的实际执行流程

要把用户问题进入系统后的路径写清楚。通常包括：

```text
接收问题
→ 理解意图
→ 判断是否需要工具
→ 选择知识库、记忆或外部工具
→ 执行调用
→ 处理结果或错误
→ 组织最终回答
```

实际流程必须以系统真实行为为准，而不是以设计文档中的理想行为为准。测试时既要检查最终回答，也要检查中间过程是否正确，例如是否选对工具、参数是否正确、调用顺序是否正确、失败后是否正确处理。

## 4. 设计完整的测试问题

每类功能都要设计一组测试问题，不能只使用一个最标准的成功案例。

测试问题至少应覆盖以下几类：

### 4.1 正常场景

用户按照预期方式提出清晰、完整的问题，验证主流程能否正确完成。

### 4.2 边界场景

测试输入缺少信息、信息过多、条件冲突、结果为空、数据量极大或极小时，系统是否仍然符合预期。

### 4.3 异常场景

测试知识库、记忆、搜索服务、数据库或模型不可用、超时、返回错误数据时，Agent 是否能够停止错误扩散并给出合理说明。

### 4.4 越界和安全场景

测试用户要求 Agent 做它不应该做的事情、要求泄露内部信息、要求伪造结果，或者试图改变系统规则时，Agent 是否能够拒绝或安全降级。

### 4.5 连续和组合场景

测试多轮对话、多个条件同时出现、前一个问题影响后一个问题时，记忆、上下文和工具结果是否正确关联。

### 4.6 随机和变化场景

同一个问题重复执行，或使用不同表达方式执行，验证结果是否基本稳定，而不是偶然通过一次。

## 5. 定义测试标准和预期结果

每个测试问题都必须有可判断的标准，至少说明：

- 是否应该回答；
- 是否应该调用工具；
- 应该调用哪些工具；
- 工具调用顺序和参数应满足什么条件；
- 最终回答必须包含什么；
- 哪些内容不能出现；
- 遇到失败时应该如何解释或降级。

标准应该来自 Agent 的产品目标、业务规则和安全要求。AI 可以帮助生成测试标准、检查回答和进行初步评分，但不能让 AI 单独决定什么叫成功，否则可能出现“AI 自己测试自己、自己给自己打分”的问题。

对于可以程序判断的内容，应优先使用明确规则判断，例如工具是否被调用、字段是否存在、结果是否满足条件。对于相关性、解释质量和表达清晰度等内容，可以使用 AI 评分，并结合人工抽查校准。

### 5.1 固定模型与评测模型的职责

被测 Agent 的模型、模型版本、系统提示词、工具配置、温度和知识库版本应固定，作为控制变量。评测模型可以与被测模型不同，但评测提示词、评分规则和输入信息必须固定，并通过人工抽查校准，避免让评测模型单独决定成功标准。

### 5.2 开放任务和多条有效路径

开放性问题不应要求唯一答案或唯一工具顺序，而应定义必须达到的结果、约束、禁止行为和最低质量阈值。只要结果满足这些条件，允许存在多种合理的工具路径；能够程序判断的条件优先用规则判断，无法完全规则化的部分再使用 AI 评审。

### 5.3 指标、权重和通过阈值

每个能力类别应明确任务成功率、答案正确性、完整性、工具调用准确率、安全性、稳定性、延迟和成本等指标，并规定单项最低分、整体通过率和关键失败项的阻断条件。总分不能掩盖关键安全或流程错误，关键指标未达标时即使平均分较高也不能判定通过。

## 6. 自动化执行和过程记录

测试应尽可能一次性自动执行，减少人工干预。每次执行至少记录：

- 测试问题和上下文；
- Agent 的最终回答；
- 使用的模型、提示词和配置版本；
- 实际调用的工具、参数和顺序；
- RAG 或记忆返回的内容摘要；
- 外部搜索或其他服务的结果状态；
- 错误、超时、重试和降级过程；
- 执行耗时和资源消耗；
- 最终评分和失败原因。

记录完整过程的目的不是保存日志本身，而是让失败能够被复现和定位。只看最终答案，通常无法判断问题究竟出在检索、决策、工具调用、记忆、数据处理还是回答生成阶段。

### 6.1 存储分层和清理策略

测试可以按能力类别分批执行，每批完成后再进入清理流程。原始轨迹、工具返回文件和网页快照优先存放在对象存储或压缩文件中，评分、版本、失败原因和统计结果存放在轻量数据库中；重复的工具结果可以去重，较大的返回内容可以保存摘要和校验值。

只有在该批测试已经完成、报告已生成、失败原因已定位、修复和回归结果已确认并完成备份后，才能删除成功案例的完整轨迹和大型临时文件。失败案例、代表性样本、测试用例、配置版本、模型版本和关键轨迹应保留，用于复现、审计和版本比较；删除的数据之后通常不参与日常回归，但可能无法支持历史问题重现。

建议为数据设置保留级别：失败案例长期保留，成功案例保留摘要和少量样本，临时工具文件在批次结束后删除，并通过磁盘配额和保留期限自动清理。

## 7. 结果评估和问题定位

执行完成后，将实际结果与预先定义的标准进行比较，并区分两件事：

1. **结果是否正确**：最终回答是否满足用户目标和约束。
2. **过程是否正确**：Agent 是否通过正确的路径得到结果。

常见问题位置包括：

- 意图理解错误；
- 不该调用工具时调用了工具；
- 需要调用工具时没有调用；
- RAG 检索不到、检索错误或结果没有被使用；
- 外部搜索失败、结果过期或结果被错误理解；
- 记忆读取错误、保存错误或用户之间发生串用；
- 工具参数错误或调用顺序错误；
- 异常没有被捕获，或者错误被伪装成成功；
- 最终回答遗漏条件、虚构事实或表达不清。

每个失败案例都应该形成可追踪记录：输入、预期、实际、失败阶段、根本原因、修复方案和修复后的结果。

## 8. 修复和回归测试

修复应针对失败的根本原因，而不是只针对某一道题修改答案。

修复后至少要做两类测试：

- **针对性复测**：确认原来的失败案例已经修复；
- **回归测试**：确认修复没有破坏其他已经通过的功能。

如果修改了提示词、模型、工具、RAG、记忆、数据格式或流程判断，都应重新执行受影响的测试集。稳定的测试集和测试结果记录，是判断系统是否真正变好的基础。

### 8.1 版本化和控制变量

修复前先建立基线版本（V0），每次尽量只修改一个问题或一个变更批次，并为模型、提示词、工具、RAG、记忆、代码和配置记录版本号。每个版本都应运行当前能力测试集和完整回归测试集，比较整体分数、各能力分数、通过率、失败案例、Token、延迟和成本。

如果一次同时修改多个变量，只能把它们作为一个变更批次评价，不能把效果归因给其中某个修改。版本比较至少应保留测试摘要、失败样本、配置清单和评测规则，即使删除大型原始轨迹，也必须能够解释版本之间的差异。

## 9. 测试通过和上线判断

测试“通过”不应只表示有几个问题回答得很好，而应表示：

- 主要功能能够完成；
- 边界情况有合理行为；
- 异常时不会编造或误报成功；
- 工具和数据过程基本正确；
- 关键失败能够被发现、记录和复现；
- 修复后的结果通过回归测试；
- 多次执行结果具有足够稳定性。

达到这些条件后，才可以进入上线阶段。上线前还应确认有基本的日志、错误追踪和运行监控，因为测试只能覆盖已设计的场景，不能证明线上永远不会出现新问题。

## 10. 给 AI 执行测试时的通用指令结构

后续可以按以下结构把任务交给 AI：

```text
1. 读取 Agent 的目标、功能类别和限制。
2. 梳理每类功能的实际执行流程。
3. 为每类功能生成正常、边界、异常、越界和组合测试问题。
4. 为每个问题定义可验证的预期结果和失败条件。
5. 自动执行全部测试并保存完整过程记录。
6. 使用规则检查和 AI 评估比较实际结果与预期标准。
7. 按失败阶段和根本原因分类问题。
8. 提出并实施修复。
9. 重新执行失败测试和完整回归测试。
10. 输出测试报告、未解决问题和上线风险。
```

AI 的最终输出不应只有一个总分，还应包括：通过和失败的测试、失败发生的过程节点、问题原因、修复内容、回归结果，以及仍然无法确认的风险。

建议报告至少包含：测试批次和时间、Agent 与评测模型版本、测试集和能力类别、各项指标及阈值、通过/失败用例、失败阶段和根因、修复变更、版本对比、Token/耗时/成本、保留与清理的数据清单，以及未解决风险。

## 11. 方法的核心原则

这套方法可以归纳为五句话：

1. 先定义 Agent 应该做什么，再测试它实际上做了什么。
2. 既测试正常结果，也测试边界和失败处理。
3. 既检查最终答案，也检查产生答案的过程。
4. AI 可以辅助生成标准和评分，但关键标准必须由目标和规则约束。
5. 每次修复都必须经过回归测试，并在上线后持续观察。
