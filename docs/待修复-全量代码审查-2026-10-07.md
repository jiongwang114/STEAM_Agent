## P0：先修复的行为和安全问题

### P0-01 Guard 阻断会把内部标记当成功答案返回

- 位置：`graph/nodes.py:343-365`、`graph/builder.py:58-67`、`api/routes.py:665-697`。
- 证据：Guard 节点将 `GUARD_BLOCK:...` 放入 `AIMessage` 后，路由直接 `END`，没有 `termination_reason`、安全兜底节点或公开错误事件。API 在回复为空时会反向取最后一个没有 `tool_calls` 的消息，因此会把 `GUARD_BLOCK:` 文本规范化为 `reply`；随后 `termination_reason` 默认成 `completed`，`status` 仍可能是 `success`。
- 影响：越权/危险请求的用户能看到内部协议和 guard 原因；监控把拦截记为成功，评测和前端无法区分拒答与正常回答。
- 建议：增加明确的 `guard_block` 状态节点或统一终止结果；公开固定的安全提示，内部原因只写日志；API 提取回复时排除 `GUARD_BLOCK:`；为同步和 SSE 定义同一错误码、`degraded/blocked` 状态并记录指标。
- 验收：每一类 Guard 拒绝都只能得到用户可读拒答；响应中不存在 `GUARD_BLOCK`、工具协议或敏感规则；状态码/事件/指标均标记 blocked。

### P0-02 结构化 JSON 输出绕过大部分证据校验

- 位置：`prompts/modules.py:127-151`（要求 `{summary,games:[...]}` JSON）、`api/routes.py:478-515`（规范化 JSON）、`graph/nodes.py:762-815,907-1022`。
- 证据：校验器通过 Markdown `[名称](https://store.steampowered.com/app/id)` 的文本区段寻找名称、价格、Metacritic、折扣；当前主提示和 API 却把 `store_url/name/price/...` 放在独立 JSON 字段。结构化响应中通常没有符合正则的 Markdown 链接，所以名称和数值违规不会生成 violation，repair 不会触发。即使有 URL，当前代码只用 URL 中的 appid 校验存在证据，未校验 `store_url` 的域名和 URL appid 与字段 appid 一致。
- 影响：模型可以返回证据中不存在的游戏名、价格、评分、折扣，仍被判定为通过；这会直接破坏“证据约束推荐”的产品承诺。
- 建议：先解析 canonical envelope，再按 `games[*].appid` 与 evidence 建立字段级比较；名称、价格、评分、折扣、URL 分别校验；URL 只允许 `https://store.steampowered.com/app/<appid>`（必要时加受信图片域名）；解析失败必须进入 repair/fallback。
- 验收：用 JSON 形式伪造名称、价格、评分、第三方 URL，均被拒绝或修复；合法字段通过；Markdown 兼容分支仍有同等规则。

### P0-03 API 流式回复缓存可能覆盖校验后的安全兜底

- 位置：`api/routes.py:554-598,665-746`、`graph/nodes.py:818-897`。
- 证据：API 监听 `finalize` 和 `repair` 的 `on_chat_model_stream`，把每一段直接累加进 `reply`。LangGraph 后续可能进入 `safe_fallback`（只追加一条非流式 AIMessage）或预算 fallback；此时 API 只有在 `reply` 为空时才从最终 state 取消息。只要 repair 产生过文本，safe fallback 的最终安全答案就不会覆盖它；多次 repair 的流式片段也可能拼接成协议文本。若 JSON 规范化失败，用户会收到最后一段未验证文本。
- 建议：流式阶段只发送预览，最终以 checkpoint 中经过 validate 的 canonical message 作为唯一响应源；`safe_fallback`、budget 和 guard 必须有明确终止结果；在 `done` 前重新解析并验证最终 envelope，失败则只发送安全兜底。
- 验收：验证失败、修复超预算、模型中断、Guard 阻断四条路径都返回对应最终状态，不能出现上一版 repair 文本或内部协议。

### P0-04 Agent 图的约束提取在标准 API 路径中被初始化值短路

- 位置：`graph/run_context.py:15-49`、`api/routes.py:537-544`、`graph/nodes.py:54-65`、`graph/constraints.py`。
- 证据：`new_run_context()` 每次显式写入 `constraints=[]`；`initialize_context_node` 只有在 key 不存在时才调用 `extract_constraints`，因此正常 API 请求永远不提取“免费/多人/年份”等条件。即使手工注入约束，`update_constraint_status` 只写状态、不写 evidence ids；多人判断用对整个对象的 `repr` 搜索 `multiplayer`，`has_multiplayer=False` 也可能被判为满足；约束状态没有传给 `SearchPlan`，也没有成为 validate gate。
- 影响：硬约束静默丢失，检索可能返回付费、单人或年份不符的推荐。
- 建议：从当前 human message 提取并写入 state；定义 typed constraint/evidence 结构；按字段值判断满足关系；将约束映射到工具/RAG where；在证据缺失时阻止最终推荐。
- 验收：针对每个硬约束有可追踪状态、证据 appid 和失败原因；不满足时只能澄清或 fallback。

### P0-05 Graph 初始化在异步事件循环中持有同步锁跨越 await

- 位置：`graph/builder.py:19-41`。
- 证据：`build_graph` 是 async 函数，却在 `threading.Lock` 内执行 `await aiosqlite.connect(...)`。两个不同线程/请求首次并发初始化时，第二个协程会同步阻塞事件循环等待锁；第一个协程无法继续运行到连接完成并释放锁，存在死锁/长时间卡死路径。单例连接和图也没有 lifespan shutdown/重建逻辑。
- 建议：使用进程内 `asyncio.Lock`，锁外不做同步等待；在应用 lifespan 预初始化并显式关闭 checkpointer/连接；为数据库损坏或 rotate 提供清理和重建。
- 验收：并发冷启动不会阻塞；连接异常可恢复；应用关闭无未关闭连接和任务。

### P0-06 工具超时只取消 Future，不会取消已运行的阻塞调用

- 位置：`tools/executor.py:19-20,96-126,136-148`。
- 证据：超时后 `future.cancel()` 对已运行线程无效；外部 HTTP/SQLite 调用仍占用全局 `_POOL(max_workers=8)`。每个工具最多重试三次，批量执行又把 futures 全部永久 `result()`，没有 batch 级截止时间。
- 影响：上游超时期间线程持续堆积，重试会放大故障，最终导致工具线程池饥饿和所有 Agent 请求变慢；API 的 wall deadline 无法真正停止后台工作。
- 建议：优先把工具改为可协作取消的 async/httpx 调用；至少为每个外部调用传递 deadline；批量等待采用统一 deadline；将重试和并发上限按工具隔离并计数；进程 shutdown 时关闭 executor。
- 验收：连续超时不会累积运行线程；批量调用在总预算到期时返回明确的 timeout；重试数、活动线程和丢弃调用可观测。

## P1：生产可靠性、隔离和数据一致性

### P1-01 流运行状态只在进程内，无法支撑多 worker 或实例

- 位置：`api/routes.py:57-175,817-844`。
- 证据：`_chat_runs`、监听队列、`asyncio.Task` 和 thread lock 都是进程内对象；`GET /chat/runs/{thread_id}` 只能找到当前进程的运行。部署 workflow 没有声明单 worker 约束，后续横向扩展时刷新/重连可能落到另一实例。
- 建议：明确单进程运行限制，或把 run event/snapshot 放到 Redis/持久队列；SSE 只作为订阅，不作为运行状态存储；用 run_id 而非仅 thread_id 做幂等键。

### P1-02 前端旧流的 finally 会清理新会话/新请求状态

- 位置：`night-museum-frontend/app.js:181-185,391-412`。
- 证据：切换/新建会话会 abort 旧 controller 后立即 `busy=false`；旧 `runMessage` 的 finally 无条件清 `state.busy`，`attachRun`/`continueGeneration` 还未统一设置 busy 和 controller。旧请求完成时可解除新请求锁、清掉新 `state.stream`，随后允许并发发送或错误地显示旧事件。
- 建议：为每次运行生成 generation/run_id；所有回调和 finally 只在 controller/generation 仍是当前值时修改 state；attach/continue 与 send 共用同一 busy 生命周期；切换会话时清理旧 listener。
- 验收：快速切换会话、重连、停止、继续生成和重复点击不会串消息、解锁错误或重复归档。

### P1-03 SSE snapshot 没有恢复累计 reply，重连可能丢回答

- 位置：`night-museum-frontend/app.js:378-382`。
- 证据：snapshot 只更新 stage/error，没有把 `snapshot.reply` 写入 `assistant.rawContent/content`。如果重连时没有后续 token，界面会显示空回答，尽管服务端 snapshot 已有累计内容。
- 建议：snapshot 与 token 使用同一 canonical buffer；先设置 raw/replay content，再等待 done；按 run_id 丢弃过期 snapshot。

### P1-04 生产前端允许 `?api=` 把登录请求发往任意 Origin

- 位置：`night-museum-frontend/app.js:60-75,107-120`。
- 证据：任意 URL 查询参数都成为 `apiBase`，所有请求都带 `credentials: include`；攻击者可诱导用户打开带 `?api=https://attacker` 的页面，把登录/注册密码发送到攻击端（攻击端只需配合自己的 CORS）。
- 建议：生产构建禁用 query override；仅在显式开发模式允许 localhost allowlist；生产使用 same-origin 或固定配置，配合 CSP `connect-src`。
- 验收：生产 URL 的任意 `api` 参数都被忽略或拒绝；登录请求永远只发到受信 API。

### P1-05 推荐 URL 和图片 URL 未做后端/前端 allowlist

- 位置：`api/routes.py:500-515`、`night-museum-frontend/app.js:232-270`。
- 证据：后端对 `store_url/image_url` 只执行 `str()`；结构化和表格解析路径接受任意 URL，前端随后直接写入 `img.src` 和 `a.href`，CSS 预览还把图片值插入 `url(...)`。Markdown 正则路径虽限制 Steam 域名，但不是主路径。
- 影响：可出现伪 Steam 链接、第三方跟踪/图片请求；URL scheme、重定向和 CSS 注入边界不明确。
- 建议：后端用 URL 类型和 scheme/host/appid 校验；前端二次拒绝非 HTTPS/非 allowlist；设置 CSP `default-src/img-src/connect-src`；不要把未验证 URL 拼入 CSS。

### P1-06 异步记忆队列是未接入的完整死链路，文档却声称启动 worker

- 位置：`memory/async_memory.py:58-375`、`memory/message_store.py:103-105`、`api/main.py:54-67,81-106`、`config.py:86-100`、`docs/BACKEND_DEPLOYMENT.md:28,77-81`。
- 证据：队列表、租约、重试、LLM 提取和配置都存在，但全仓没有调用 `enqueue_memory_extraction` 或 `run_pending_memory_tasks`；归档只写 `messages/execution_summaries`。API lifespan 只有 thread cleanup worker，没有 memory worker。
- 影响：用户明确要求记忆时，只有同步工具路径可能写入；后台记忆提取实际上不会运行，文档/配置形成错误运维预期；整套依赖、迁移和模型代码增加维护面。
- 建议二选一：接入真正的持久化 worker（归档事务内 enqueue，lifespan 或独立 worker 领取，shutdown/circuit/指标齐全），或删掉未接入实现和配置并更新文档。不要保持“默认启用但没有消费者”。
- 验收：明确有可观测的 pending→running→completed/failed 生命周期，或仓库中不再声称该能力存在。

### P1-07 归档/线程元数据的建表和迁移在请求热路径重复执行

- 位置：`memory/auth.py:163,192,241,255,275,287,296,318`、`memory/message_store.py:108,150,192,217,282,296,317,499,534,549`、`memory/thread_title.py:52,67,79,90,118,134,148`、`memory/session_summary.py:45,72,103`。
- 证据：几乎每个读写函数都调用 `init_*_table()`，其中包含 DDL、`PRAGMA journal_mode=WAL`、`PRAGMA table_info` 和迁移；热请求会重复获得 SQLite 写锁并打开/关闭多个连接。
- 影响：额外延迟、锁竞争、并发初始化失败概率和不可预测的 schema 迁移时序；数据库故障被大量宽泛异常掩盖。
- 建议：启动阶段一次性执行版本化 migration；读路径只获取连接；集中连接工厂和事务策略；用 schema version/迁移锁保证跨进程顺序。

### P1-08 `archive_sqlite_turn` 和旧兼容 API 的轮次写入契约不统一

- 位置：`memory/message_store.py:108-139,142-189,231-240`、`memory/archiver.py:9-34`。
- 证据：主路径在一个事务中分配轮次并写 user/assistant；仍公开 `reserve_turn_number`、`add_message` 兼容函数。`messages` 表没有 `(user_id,thread_id,turn_number,role)` 唯一约束，调用兼容函数可写重复轮次；`archive_sqlite_turn` 的 `turn_number` 参数在 archiver 签名中存在但完全未使用。
- 建议：删除无调用兼容接口，或统一到一个 service；增加唯一约束/迁移和幂等键；移除未使用参数并在文档写明轮次分配的唯一来源。

### P1-09 Steam profile cache 使用阻塞 urllib、宽泛吞异常且无负缓存/并发合并

- 位置：`memory/game_profile.py:40-91,94-177`。
- 证据：profile 获取使用同步 `urllib.request.urlopen`，15 秒 + 10 秒串行请求；多个请求同一 Steam ID 会重复打上游；所有异常返回空字符串，无法区分私密档案、限流、网络故障或缓存缺失。
- 建议：统一 httpx client、连接池、指数退避和状态分类；按 Steam ID 做 single-flight；加入短期负缓存和指标；保证调用发生在明确的线程/async 边界。

### P1-10 用户绑定后同一 checkpoint 可能继续使用旧 Steam ID

- 位置：`graph/nodes.py:68-82`、工具上下文注入处（优先 `steam_id_snapshot`）、`api/routes.py:973-1010`。
- 证据：初始化只在 state 缺少 `steam_profile_snapshot` 时保存 `steam_id_snapshot`；之后重新绑定 Steam ID 时，已有线程 checkpoint 仍优先使用旧 snapshot。
- 建议：明确绑定变更的会话语义：绑定后使相关 checkpoint 失效/刷新 snapshot，或在每轮校验绑定版本；工具不得静默使用旧身份。
- 验收：重新绑定后新请求不会读取旧 Steam 库；历史线程的行为有公开、可测试的刷新规则。

### P1-11 配置在 import 时强制读取密钥并只做局部校验

- 位置：`config.py:6-44,117-152,221-230`。
- 证据：导入 `config` 即要求 `DEEPSEEK_API_KEY`、`STEAM_API_KEY` 环境变量；大量数值只直接 `int/float`，没有统一配置模型和字段来源审计；`SESSION_COOKIE_SECURE` 默认 false。这样会让离线工具、静态检查和迁移命令无法导入模块，也容易把生产 cookie 安全属性遗漏。
- 建议：用 Pydantic Settings 分层校验，启动时才按服务能力检查必需密钥；离线 RAG/迁移命令允许显式 profile；生产环境默认 secure=true，并校验 `SameSite=None` 与 secure 的组合。

### P1-12 日志和 trace 上下文存在重复实现，且 trace 字段未保证注入/清理

- 位置：`api/routes.py:440-450`、`graph/run_context.py:52-70`、`tracing.py`、`api/routes.py:527-535`。
- 证据：token usage 提取有两份实现；`tracing.get_trace_metadata` 无调用；`set_trace_context` 没有返回/reset token，metadata 也未明确并入 LangChain config。跨请求 contextvar 可能残留或无法出现在实际 LangSmith run 中。
- 建议：保留一个 usage parser；统一 `set/reset` 上下文管理器；将 user/thread/run_id 作为显式 runnable metadata，并写不含敏感值的 trace 测试。

## P1：RAG、索引和评测一致性

> 本节的索引与评测问题均来自静态核对代码、manifest 和锁文件；没有加载索引或运行评测。

### P1-13 已提交 manifest 与部署锁文件的运行时版本不一致

- 位置：`requirements-rag-lock.txt`、`rag/eval_index_cloud_20261006/index_manifest.json`、`rag/eval_index_frozen_20261005/index_manifest.json`、`rag/vector_store.py:78-123`。
- 证据：锁文件声明 `sentence-transformers==5.5.1`、`torch==2.12.0+cpu`、`transformers==5.9.0`；cloud manifest 声明 sentence-transformers 5.6.0、运行时 torch 2.13.0+cu130、transformers 5.13.1，frozen manifest 也记录不同版本。`index_compatibility()` 会逐项比较 Chroma、sentence-transformers 和 manifest runtime versions，部署到锁定环境很可能被判 incompatible。
- 建议：索引构建和部署共用 lock/容器 digest；manifest 保存完整 Python/OS/CPU runtime；CI 在发布前运行 compatibility check，不能把 working-tree 索引当生产产物。

### P1-14 RAG 索引发布不是全代原子切换

- 证据：当前索引、共享 cache、manifest 和 collection 位于同一可变目录，构建流程会先写共享文件，再切换 `current_index.json`；没有跨进程写锁、临时目录校验或版本目录的原子 rename。
- 影响：服务可能读到新 cache+旧 collection、旧 manifest+新 collection 或半写 JSON；ready 检查不能修复已经混合的版本。
- 建议：构建到不可变版本目录，完成向量计数、hash、compatibility 和 smoke 后原子替换一个小的 pointer；旧版本保留回滚；读取时按 pointer 解析同一版本的全部资源。

### P1-15 硬过滤在 RRF top-N 后才执行，可能丢掉满足条件的候选

- 位置：`rag/hybrid.py:60-110`。
- 证据：dense/lexical 先召回，RRF 先截断 `fused[:RAG_RERANK_CANDIDATES]`，之后才对 `post_filter` 和 genre 做过滤；`required_genre` 在索引里找不到时还被置空（47-51），过滤请求于是退化为无过滤语义。
- 影响：结果数量不足、过滤召回率不稳定；用户的免费/多人/类型硬约束可能被静默弱化。
- 建议：可表达的过滤必须在各召回源或足够大的候选池中先过滤；不可表达的字段要明确返回 unsupported/zero-result，不得把 hard filter 改成 semantic-only；为过滤召回单独评测 precision/recall。

### P1-16 lexical index 缓存只按 collection name 失效

- 位置：`rag/hybrid.py:163-184`。
- 证据：BM25 index 只在 `_index_collection_name != current_games_collection_name()` 时重建；同 collection 名下 cache JSON 被更新、标签被补抓或内容 hash 变化时，进程继续使用旧 documents/index。
- 建议：pointer 中携带 cache hash/manifest version，缓存 key 同时绑定版本；热更新时构建新 index 后原子替换；记录 index version 和命中时间。

### P1-17 dense 错误被吞掉并退化为 lexical 成功，调用方看不到统一降级语义

- 位置：`rag/hybrid.py:61-73,144-158`。
- 证据：dense 任意异常被捕获为 `dense_error`，函数仍返回正常 results；上层工具若只读取 results，会把 embedding/Chroma 故障当成完整 hybrid 结果。
- 建议：返回明确的 `degraded` 状态和可操作错误码；如果请求含必须 dense 的能力则 fail closed；指标区分 dense failure、empty retrieval 和正常 lexical-only。

### P1-18 `/ready` 可能在探针请求中加载 embedding 模型

- 位置：`api/main.py:289-305`、`rag/vector_store.py:93-110,128-133`。
- 证据：就绪检查会调用 `index_compatibility()`；该函数计算 embedding dimension 时调用 `get_embedder()`。模型未 warmup 时，探针本身可能触发重加载/下载/高内存；多个探针并发还会放大开销。
- 建议：启动时完成一次兼容性快照，ready 只读取结果和轻量文件/collection count；模型加载失败由启动状态记录，不在每次探针执行。

### P1-19 RAG 评测配置共享进程缓存，配置间结果和延迟不可横向比较

- 位置：`rag/evaluation/run.py:146-186`。
- 证据：多个 configuration 在同一进程顺序执行，共享 hybrid 的 BM25、Chroma client、embedding/reranker LRU；每组只做一次中性 warmup，先跑的配置会为后续配置改变缓存和模型状态，latency 也混入缓存热度差异。
- 建议：为每个配置记录 cold/warm 语义；随机化或独立进程运行；固定 query translation/embedding cache 策略并报告缓存命中，避免把不同缓存状态的延迟做横向结论。

### P1-20 评测 runner 把 unsupported filter/空结果与通过率混在一起

- 位置：`rag/evaluation/run.py:159-185`。
- 证据：Filtered-Hybrid 对不可表达过滤默认写 `skipped_unsupported_filters`；aggregate 只统计 executed rows，valid_execution 只检查 dense/reranker 错误，报告没有独立的 filter precision/recall（固定为 None）。
- 建议：将 skipped、empty、error、executed 分列；为硬过滤建立独立 gold labels；valid_execution 同时要求覆盖率阈值和 filter contract；报告 query translation、数据版本和配置 hash。
