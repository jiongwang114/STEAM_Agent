# 会话、记忆与持久化实施文档

## 当前状态

项目有四类重要状态：LangGraph 对话检查点、SQLite 结构化消息、SQLite 用户画像、Chroma 语义记忆。聊天结束后会同时写 Chroma 和 SQLite。线程删除也尝试清理这几层数据。

当前主要问题是：轮次计数保存在进程内；双写没有统一事务；检查点和删除逻辑没有完全使用用户级隔离；部分清理异常会被静默忽略。

## 目标

用户看到的会话历史、Agent 继续对话的上下文、长期记忆和删除结果应该保持一致。服务重启不应改变历史顺序，也不应覆盖旧消息。

## 实施方案

### 1. 持久化轮次和消息编号

- 为 `(user_id, thread_id)` 建立唯一的顺序来源。
- 轮次号由数据库事务分配，不由进程内字典决定。
- Chroma 文档 ID 使用不可重复的消息/回合 ID，避免服务重启后覆盖旧向量。
- 同步接口和流式接口共用同一套归档函数。
- 并发请求要么排队，要么明确返回“该会话正在处理中”。

### 2. 双写可靠性

建议将一次归档视为一个可追踪任务：

1. 先在 SQLite 写入归档任务和消息状态。
2. 写入 Chroma 成功后标记完成。
3. Chroma 失败时保留待补偿记录，不影响用户得到明确的归档状态。
4. 提供 `reindex` 或补偿命令，从 SQLite 重新构建语义记忆。

SQLite 和 Chroma 不能共享真正的事务，因此重点是“可恢复”和“可核对”，而不是假装两边绝对原子。

### 3. 线程删除

删除应以 `(user_id, thread_id)` 为条件，逐层记录结果：

- 消息表
- 线程标题
- LangGraph checkpoints/writes
- Chroma user memory

删除失败不得静默吞掉；接口应返回“已删除”或“部分删除，后台继续处理”，运维日志要能看到失败层和原因。

### 4. 用户画像与游戏档案

- 用户偏好继续由 SQLite 结构化保存，保留来源、置信度、范围和过期时间。
- 检查同一主题的正向和负向偏好是否正确替代。
- 明确 Steam 游戏档案是“缓存数据”还是“长期记忆”，不要混在两者之间。
- 如果要用于推荐，应把档案注入系统提示词，并限制最大长度。
- 如果暂不接入 Agent，应在文档中明确它只是绑定后的预热缓存。

## 验收标准

- 服务重启后继续同一会话，历史顺序和用户身份不变。
- 同一回合不会出现两个不同轮次号，也不会覆盖 Chroma 旧记录。
- SQLite 有而 Chroma 没有时，可以通过命令补齐；反过来也能发现异常。
- 删除线程后，历史 API、Agent 检查点和语义召回都无法再找到该线程内容。
- 用户 A 的记忆不会被用户 B 检索出来。

## 必须补的测试

- 重启前后继续对话。
- 同一线程同步和流式请求并发。
- 归档时模拟 SQLite 成功、Chroma 失败以及相反情况。
- 删除时逐层注入失败。
- 记忆重建后数量、metadata 和检索结果一致。
