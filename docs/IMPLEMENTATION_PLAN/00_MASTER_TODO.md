# Steam Agent 总待实现清单

更新时间：2026-09-25

这份清单按“风险优先、依赖优先”的顺序排列。它不是把所有想法都堆在一起，而是定义从当前单机 Agent 走向可靠服务所需要完成的工作。

## 一、当前最重要的结论

当前项目已经具备可运行的推荐链路、工具治理、混合 RAG、记忆和评测框架，但仍有几个上线级风险：

1. API 接口信任客户端传入的 `user_id`，登录后没有服务端会话或访问令牌。
2. 密码使用普通 SHA-256，且登录接口通过查询参数接收密码。
3. LangGraph 检查点主要按 `thread_id` 隔离，删除检查点和语义记忆也主要按 `thread_id` 操作。
4. 轮次计数保存在进程内，服务重启或多进程运行时可能重复或错乱。
5. README 宣称三层安全检查，但当前运行图实际没有接入 `layer2_intent`。
6. 游戏画像已实现缓存，但没有真正注入 Agent 的系统提示词。
7. RAG 重建会先删除旧集合；摄入脚本获取热门游戏时使用了 `PLACEHOLDER` key，重建流程缺少原子替换。
8. 文档中的目录、工具数量和评测基线与当前代码存在版本差异。

## 二、实施顺序

```text
P0 身份与隔离
  ↓
P0 会话与数据一致性
  ↓
P0 安全策略与运行边界
  ↓
P1 RAG 数据可靠性、API/部署加固
  ↓
P1 测试和评测门禁
  ↓
P2 个性化、性能和文档持续改进
```

## 三、P0：上线前必须完成

### A. 身份、授权和数据隔离

- [ ] `SEC-001` 设计服务端登录会话：明确 token/cookie 方案、过期时间、退出登录和撤销机制。
- [ ] `SEC-002` 所有用户相关接口从服务端会话取得用户身份，不再信任请求中的 `user_id`。
- [ ] `SEC-003` `/chat`、`/chat/stream`、线程、消息、Steam 绑定、主题和用户信息接口增加授权校验。
- [ ] `SEC-004` 统一使用用户级线程键，例如 `user_id + thread_id`；同步修改锁、检查点、归档、删除和记忆查询。
- [ ] `SEC-005` 密码改为 Argon2id 或 bcrypt；禁止在 URL 查询参数中传递密码。
- [ ] `SEC-006` 增加注册、登录、绑定 Steam 的输入校验、频率限制和审计日志。
- [ ] `SEC-007` 对已有用户和历史数据设计迁移及回滚方案。

验收：用户 A 无法读取、修改、删除或影响用户 B 的会话、画像、记忆和 Steam 绑定；服务重启后隔离规则仍成立。

### B. 会话、归档和删除一致性

- [ ] `DATA-001` 将轮次号或消息序号持久化到 SQLite，不再只依赖进程内 `_turn_counter`。
- [ ] `DATA-002` 让同步和流式接口使用同一套“生成结果、归档、编号、指标”逻辑。
- [ ] `DATA-003` 为 Chroma 与 SQLite 双写增加失败记录、重试或可执行补偿任务。
- [ ] `DATA-004` 删除线程时按用户和线程双重条件清理四层数据，并记录每层清理结果。
- [ ] `DATA-005` 验证服务重启、多进程和同一线程并发时不会重复覆盖历史消息。
- [ ] `DATA-006` 明确删除的语义：立即删除、异步删除还是标记删除，并补充用户可见反馈。

验收：连续重启、并发请求和删除后恢复测试均通过；SQLite、检查点、线程标题和 Chroma 没有残留或错配记录。

### C. Agent 安全与终止边界

- [ ] `AGENT-001` 明确安全层级并修正文档；若保留 Layer 2，就将 `layer2_intent` 接入运行图。
- [ ] `AGENT-002` 定义安全分类服务失败时的策略：对越狱检测和红线检测不能无条件静默放行。
- [ ] `AGENT-003` 验证 token、时间、工具轮次和单工具配额在所有退出路径都生效。
- [ ] `AGENT-004` 检查预算耗尽时 finalize 自身是否需要预留 token，避免“已经超预算后又调用模型”。
- [ ] `AGENT-005` 为最终答案校验补充价格、评分、折扣、链接和协议泄露的边界测试。

验收：任何输入都能在预算内结束；模型无法突破工具政策；安全服务异常时有明确、可解释的降级行为。

## 四、P1：近期完成

### D. RAG 和游戏知识库

- [ ] `RAG-001` 修复热门游戏摄入的认证和数据来源问题，移除 `PLACEHOLDER` 请求参数。
- [ ] `RAG-002` 统一默认抓取数量、当前缓存数量和文档说明，避免“默认 250、实际 418”混淆。
- [ ] `RAG-003` 改为新目录构建、校验通过后再切换的原子索引更新流程。
- [ ] `RAG-004` 为索引保存数据 hash、模型版本、代码版本、构建日志和失败原因。
- [ ] `RAG-005` 增加索引版本检查：应用启动时发现索引与配置不兼容，要给出明确告警。
- [ ] `RAG-006` 评估中文关键词、游戏专名、冷门游戏和 reranker 失效时的召回质量。
- [ ] `RAG-007` 为知识库增加定期更新、去重、下架游戏和价格信息时效边界说明。

### E. API、前端和部署

- [ ] `API-001` 将敏感和写入参数从 query 参数迁移到 JSON body。
- [ ] `API-002` 将 `/health` 区分为进程存活检查和依赖可用检查。
- [ ] `API-003` 对流式请求补充取消、断开、重复提交和归档失败处理。
- [ ] `API-004` 明确单进程运行约束；若要多 worker，先解决锁、指标和 SQLite 写入问题。
- [ ] `API-005` 统一 `docker-compose.yml`、`deploy.sh` 和 `restart.sh` 的端口、数据卷和启动方式。
- [ ] `API-006` 对 `/metrics`、认证接口和错误响应制定访问与脱敏规则。
- [ ] `API-007` 增加代理、HTTPS、CORS、请求体大小和基础限流配置说明。

### F. 测试、评测和可观测性

- [ ] `QA-001` 增加跨用户授权和数据隔离测试。
- [ ] `QA-002` 增加重启后会话、轮次和归档恢复测试。
- [ ] `QA-003` 增加索引重建失败、旧索引保留和 manifest 不匹配测试。
- [ ] `QA-004` 增加真实 API schema、SSE 事件顺序和客户端断开测试。
- [ ] `QA-005` 统一 RAG 基线数字，注明数据集、代码版本、索引版本和模型版本。
- [ ] `QA-006` 为安全分类错误、工具超时、熔断、重复调用和证据不足建立回归用例。
- [ ] `QA-007` 监控请求成功率、降级率、TTFT、P95、token、工具错误和索引版本。

## 五、P2：长期优化

- [ ] `P2-001` 真正接通 Steam 游戏画像到系统提示词，并评估个性化增益。
- [ ] `P2-002` 评估摘要、长上下文压缩和用户记忆注入的 token 成本。
- [ ] `P2-003` 逐步扩大游戏知识库和人工复核数据集，覆盖冷门类型和复合条件。
- [ ] `P2-004` 评估多进程/多实例部署，必要时迁移到外部数据库和集中式缓存。
- [ ] `P2-005` 建立真实流量下的成本、满意度、失败率和 A/B 评估。
- [ ] `P2-006` 统一旧文档、目录清单、设计文档和自动生成的 API 文档。

## 六、每个任务的完成定义

一个任务只有同时满足以下条件，才算完成：

- 代码实现已合入目标分支。
- 有针对性的自动化测试或可重复验证步骤。
- 失败时有明确的错误和降级行为。
- 文档已经反映当前实际行为。
- 没有引入未解释的延迟、token、成本或数据风险回归。
- 若涉及数据格式，已有迁移、备份和回滚说明。

## 七、建议的里程碑

### M1：安全可用

完成 `SEC-001` 至 `SEC-007`、`DATA-001` 至 `DATA-005`、`QA-001` 和 `QA-002`。

### M2：运行可靠

完成 `AGENT-001` 至 `AGENT-005`、`RAG-001` 至 `RAG-005`、`API-001` 至 `API-006`。

### M3：质量可证明

完成 `QA-003` 至 `QA-007`，统一评测基线，并让每次核心改动都能产生可比较报告。

### M4：体验和规模

完成画像注入、性能优化、知识库扩充和多实例部署评估。
