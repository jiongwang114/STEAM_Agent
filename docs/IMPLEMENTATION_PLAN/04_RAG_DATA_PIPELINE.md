# RAG 与游戏数据管线实施文档

## 当前状态

游戏推荐使用本地 Chroma 向量库，同时使用 BM25 关键词检索、RRF 排名融合和 CrossEncoder 重排。中文查询会调用 DeepSeek 转成英文关键词。当前游戏缓存约 418 条，并有索引 manifest 和离线评测基线。

## 已知问题

- 热门游戏摄入函数使用了字面值 `PLACEHOLDER` 作为请求参数。
- 默认抓取数量、已有缓存数量和文档说明不一致。
- 重建集合前会删除旧的 `games` collection，构建失败时可能留下不可用状态。
- CrossEncoder、embedding、翻译和 Chroma 都是运行时依赖，版本不匹配时缺少清晰告警。
- 文档中的 RAG 指标来自不同版本，不能直接比较。

## 目标

知识库更新应该可重复、可审计、可回滚；检索质量和性能要能用同一数据集、同一索引版本进行比较。

## 实施方案

### 1. 数据来源

- 明确热门榜、应用列表和手工补充数据的优先级。
- Steam API 需要 key 的接口从配置读取真实 key；不需要 key 的接口不要传占位值。
- 对 HTTP 状态码、限流、超时、空详情和下架游戏分别处理。
- 记录抓取时间、来源、请求失败数和有效游戏数。

### 2. 非破坏式重建

推荐流程：

```text
读取旧索引
  ↓
在新版本 collection/目录构建
  ↓
校验数量、hash、模型和抽样查询
  ↓
写入 manifest
  ↓
切换当前版本指针
  ↓
保留旧版本用于回滚
```

不要在新索引还未成功前删除唯一可用的旧索引。重建命令应支持 dry-run、失败退出码、保留旧版本和显式清理旧版本。

### 3. Manifest 和兼容性

manifest 至少记录：

- 数据集 hash 和有效条数
- 文档结构版本
- embedding 模型和维度
- reranker 模型
- 代码版本或 git SHA
- 构建时间、耗时和失败统计
- 当前索引版本及父版本

应用启动时检查索引模型与配置是否一致；不一致时要告警，不能静默使用旧模型生成的向量。

### 4. 检索质量

继续使用 Recall@10、MRR、nDCG、Precision、约束准确率和 hard-negative rate，但每份报告必须绑定：

- 数据集版本
- index manifest hash
- embedding/reranker 版本
- 查询翻译配置
- 代码版本

重点补测中文专名、英文专名、冷门类型、复合筛选条件、免费游戏、多人游戏和 reranker 不可用时的降级结果。

### 5. 数据时效

RAG 游戏简介适合做相似推荐；价格、在售状态和实时评分仍应来自 Steam Store。文档和回答模板必须明确两者的时效差异，避免把缓存资料说成实时状态。

## 验收标准

- 没有有效 Steam key 时，摄入命令能明确失败或使用明确的无认证数据源，不发送占位 key。
- 新索引构建失败不会破坏旧索引。
- 任意线上推荐都能追溯到当前索引版本和数据 hash。
- embedding 或 reranker 变更后不会静默混用旧向量。
- RAG 评测在相同数据和索引下可以重复得到可比较结果。

## 必须补的测试

- 抓取超时、429、5xx、空详情和部分成功。
- 新索引构建中断，确认旧索引仍可查询。
- manifest 缺失、模型不匹配、数据 hash 变化。
- 418 条缓存重建、增量添加和重复 appid。
- 翻译失败、reranker 加载失败和 dense/lexical 单路降级。
