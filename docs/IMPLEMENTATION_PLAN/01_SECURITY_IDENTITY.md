# 账号与数据安全实施文档

## 当前状态

当前有注册、登录和 Steam 绑定接口，但登录结果没有建立服务端会话。聊天和历史接口直接接受请求里的 `user_id`，因此服务端无法确认“请求者是否就是这个用户”。密码通过普通 SHA-256 保存，登录接口使用 query 参数接收密码。

## 目标

让系统能够可靠回答两个问题：

1. 这个请求是谁发出的？
2. 这个用户是否有权访问这条会话、这份记忆或这个 Steam 账号？

## 实施方案

### 1. 服务端会话

建议第一阶段使用服务端会话表：

- 登录成功后生成不可预测的随机 session token。
- 数据库只保存 token 的哈希值、用户、创建时间、过期时间、撤销时间和最后活动时间。
- 浏览器通过 `HttpOnly`、`Secure`、`SameSite` Cookie 携带会话。
- API 从会话得到 `user_id`，请求体不再决定当前用户身份。
- 增加退出登录和全部会话撤销能力。

如果后续必须支持无状态 API，再单独评估短期 JWT；不要为了方便直接把用户名放进客户端可修改的 token。

### 2. 密码处理

- 使用 Argon2id 或 bcrypt，并设置明确的工作因子。
- 新密码不能通过 URL 传递，应使用 HTTPS 下的 JSON body。
- 对旧 SHA-256 用户采用“登录成功后升级哈希”的渐进迁移，或要求统一重置密码。
- 密码错误和用户不存在返回相近的提示，避免枚举用户。
- 登录和注册增加 IP、账号维度的失败次数限制。

### 3. 授权边界

以下接口必须从服务端会话获取用户，不接受可覆盖的 `user_id`：

- `/chat`、`/chat/stream`
- `/threads`、`/messages`、`/thread-title`
- `/bind-steam`、`/steam-id`
- `/auth/user-info`、`/auth/theme`

访问线程前必须确认 `(user_id, thread_id)` 存在且属于当前用户。删除、改标题、读取消息都使用同一条授权规则。

### 4. 数据隔离键

推荐把逻辑身份统一表达为：

```text
tenant/user_id + thread_id
```

需要同步检查：

- LangGraph `configurable.thread_id`
- API 线程锁
- 轮次编号
- SQLite 消息和标题
- Chroma 的 `user_id`、`thread_id` metadata
- 检查点删除
- 评测 fixture 和测试数据

仅在 SQL 查询中追加 `user_id` 不够，因为检查点和进程内锁也必须使用同样的隔离规则。

## 验收标准

- 未登录请求不能调用用户数据接口。
- 用户 A 猜到用户 B 的 `thread_id` 也不能读取、删除或继续 B 的会话。
- 同一 `thread_id` 被两个用户使用时，底层状态不会混在一起。
- Steam ID 只能绑定到当前登录用户，不能替别人绑定或解绑。
- 密码数据库中没有明文，也不再使用裸 SHA-256。
- 登录密码不会出现在访问日志、代理日志或浏览器历史中。

## 必须补的测试

- 未登录访问每个用户接口。
- 用户 A 访问用户 B 的线程、消息、标题和 Steam ID。
- 用户 A 删除用户 B 的线程。
- 同名或相似用户名、异常长 token、过期 token、撤销 token。
- 登录限流、密码升级和错误信息一致性。
