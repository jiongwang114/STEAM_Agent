# Agent 运行时与安全策略实施文档

## 当前状态

Agent 使用 LangGraph 手写循环，节点包括 guard、agent、tools、finalize、validate、repair 和 safe fallback。代码已经具备工具轮次、单轮调用数、重复调用、总 token、总时间、超时、重试、熔断和最终证据校验。

但文档所说的“三层安全防护”与运行图不一致：当前 `guard_node` 调用了规则层和 `layer3_scope`，没有调用 `layer2_intent`。另外，安全分类调用异常时当前实现倾向返回普通结果，等同于放行，需要明确这是有意的还是风险。

## 目标

让模型负责理解和表达，让代码负责边界。无论模型如何变化，Agent 都必须能够终止、说明原因、避免重复外部请求，并且不把无证据内容说成事实。

## 实施方案

### 1. 安全检查

先确定产品政策：

- 如果需要拦截越狱和角色劫持，把 `layer2_intent` 接入图，并给它单独的超时、指标和测试。
- 如果不需要单独的 Layer 2，就删掉“三层”表述，避免运维人员误以为它已经生效。
- 对分类服务超时或返回无法识别结果，明确采用“保守阻断”还是“有限放行”。涉及成人或政治红线时建议至少进入降级答复。
- 保存分类原因和版本，但不要记录完整敏感原文到普通日志。

### 2. 预算和终止

需要同时检查四个上限：

- 总时间：包括 guard、LLM、工具、归档和流式收尾。
- 总 token：包括 guard、agent、finalize 和 repair。
- 工具轮次和单轮工具数。
- 单个工具调用次数、重试次数和结果大小。

finalize 和 repair 应预留 token，不能在已经耗尽预算后再无条件调用模型。每次结束都要写清 `termination_reason`，例如 `completed`、`deadline`、`token_budget`、`tool_budget`、`insufficient_evidence` 或 `model_error`。

### 3. 工具执行

- 所有工具使用统一的 `ToolResult` 状态。
- `empty` 不能当成异常反复重试。
- 只有幂等且可恢复的错误允许有限重试。
- 工具返回内容必须有大小上限；截断时要保留“已截断”标志。
- 工具并发只用于互不依赖的读取；写入画像的工具保持顺序。
- 模型请求的 `user_id`、`steam_id`、线程信息必须由服务端状态覆盖，不能直接信任模型参数。

### 4. 证据和答案校验

继续保留“推荐链接、价格、评分必须能在本轮证据中找到”的规则，同时补充：

- 不仅检查链接中的 appid，也检查推荐名称是否和证据对应。
- 明确“当前价格”“原价”“折扣”和“评分”的时间有效性。
- 对没有商店证据的 RAG 推荐，不自动补写价格或在售状态。
- 修复失败时只允许有限次数，最后必须返回诚实的不足说明。

## 验收标准

- 模型不能通过改参数绕过用户身份和工具配额。
- 重复调用不会产生第二次外部请求。
- 工具返回空结果时不会换关键词无限搜索。
- 预算耗尽后仍能生成可读的降级答复，且原因可追踪。
- 最终答复不泄露内部协议，不编造 appid、价格、评分或折扣。

## 必须补的测试

- Layer 1、Layer 2、Layer 3 的通过和阻断样例。
- 安全模型超时、返回空文本、返回未知标签。
- 预算分别在 guard、agent、tool、finalize、repair 阶段耗尽。
- 重复工具、空结果换参数、熔断和恢复。
- 有证据、无证据、部分证据和协议泄露的回答校验。
