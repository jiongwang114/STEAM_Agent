# Steam Agent 后端与前端实施技术文档

## 1. 文档目的

本文档用于说明当前 Steam Agent 的后端、前端和文档边界。后端实现、前端联调
和接口测试已经完成，剩余工作以实施进度中的最新记录为准。

本文档是项目的总体技术方案，不记录每次具体开发的详细过程。具体进度、接口约定和前端页面方案分别记录在：

- `IMPLEMENTATION_PROGRESS.md`：阶段进度、已完成内容、测试结果和下一步工作。
- `API_CONTRACT.md`：前后端共同遵守的接口和数据约定。
- `FRONTEND_DESIGN.md`：页面结构、视觉和交互方案及验收状态。

当前的基本原则是：

- 后端和前端共同遵守版本化的 API 契约。
- 普通聊天和流式聊天共用同一套 Agent 执行逻辑。
- 前端真实后端联调已经完成，最终视觉确认单独记录在前端设计文档中。
- 每完成一部分功能，就补充对应测试，不把所有测试推迟到最后。

## 2. 后端实施部分

### 2.1 后端目标

后端负责提供稳定、清晰、可验证的业务能力，并作为 LangGraph Agent 的统一运行入口。

后端需要保证：

- Agent 核心流程可以稳定执行。
- 登录用户、会话和 Steam 数据能够正确关联。
- 失败时返回明确结果，不产生半完成状态。
- 接口参数、返回数据和错误格式保持统一。
- 重要接口有自动化测试覆盖。

### 2.2 LangGraph 核心流程

当前 Agent 主流程为：

```text
初始化上下文
  -> 安全检查
  -> Agent 决策
  -> 工具调用
  -> 最终回答整理
  -> 答案校验
  -> 修复或安全兜底
```

普通聊天和流式聊天应当共用同一套 Agent 执行逻辑。两者的区别只在于：

- 普通聊天：等待执行结束后一次性返回完整答案。
- 流式聊天：执行过程中持续向前端返回状态和文字。

### 2.3 API 契约

后端需要整理并固定 API 契约，也就是前后端共同遵守的约定，包括：

- 接口地址和请求方法。
- 请求参数名称、类型和是否必填。
- 返回字段名称和数据类型。
- 登录凭证和用户身份确认方式。
- 流式消息的事件类型和数据格式。
- 错误状态码、错误编号和错误说明。

建议使用 OpenAPI/Swagger 维护接口文档，避免前端和后端各自理解一套规则。

### 2.4 接口分类

#### Agent 运行入口

- `POST /chat`
- `POST /chat/stream`

这两个接口负责触发 LangGraph。内部应共用同一套执行服务，避免逻辑重复。

#### 用户和业务配套接口

- 登录、注册、注销和当前用户查询。
- Steam ID 绑定和查询。
- 会话列表、消息查询、标题修改和会话删除。
- 用户主题等偏好设置。

这些接口不属于 LangGraph 节点，但为 Agent 正常工作和前端使用提供必要支持。

#### 运维接口

- `/health`
- `/ready`
- `/metrics`

这些接口用于部署、监控和故障排查，不需要由普通前端页面展示。

### 2.5 后端当前状态

1. 普通聊天和流式聊天已经共用统一执行器。
2. 认证、会话隔离、Steam 绑定、标题、删除和错误响应已经有接口测试覆盖。
3. 删除清理和异步记忆任务支持持久化记录、后台重试和受保护的立即重试接口。
4. 后续改动应优先维护 API 契约、失败恢复和跨用户隔离测试。

### 2.6 后端验收标准

- 同一套 Agent 逻辑可以支持普通和流式两种输出方式。
- 未登录用户不能调用需要身份的业务接口。
- 登录失效后，前端可以得到明确的未登录结果。
- 任何业务失败不会被错误地报告为成功。
- 绑定和删除过程中出现失败时，系统能够回滚或记录并自动补偿。
- 接口文档与实际代码保持一致。

## 3. 前端实施部分

### 3.1 前端目标

前端负责把后端能力转化为用户可以操作的页面。它不只是展示内容，还负责：

- 页面布局和样式。
- 按钮、输入框、弹窗和页面切换等交互。
- 调用后端接口并处理返回结果。
- 管理登录、当前会话、消息加载和流式输出等状态。
- 展示加载中、失败、空数据和未登录等状态。
- 对用户输入和后端返回内容进行安全处理。

### 3.2 旧前端与当前前端

旧前端把 HTML、CSS 和 JavaScript 集中在一个 `static/index.html` 文件中。该文件
保留用于兼容和回退，不作为新功能的主要实现位置。

- 当前前端位于 `frontend/`，使用 React + Vite 和独立的接口、组件、状态及样式层。
- 页面已覆盖认证、会话、历史消息、执行摘要、SSE 聊天、Steam 绑定和主题设置。

### 3.3 前端重构方向

当前前端按以下职责拆分：

- 页面和组件文件。
- 接口调用文件。
- 登录和会话状态管理文件。
- 样式文件。
- 数据类型和接口模型由接口服务层维护。
- 视觉冒烟和真实后端端到端测试位于 `frontend/scripts/`。

当前前端技术栈已确定为 React + Vite，代码位于独立的 `frontend/` 工程；页面布局按
`FRONTEND_DESIGN.md` 实施，视觉 token 和样式保持在前端独立样式层，便于后续继续调整。

### 3.4 前端接口接入原则

- 严格按照后端 API 契约发送请求和解析数据。
- 不直接猜测字段名称或错误格式。
- 登录状态以服务端确认结果为准，不能只依赖浏览器缓存。
- 对聊天流式消息统一处理状态、文字和结束事件。
- 对接口失败提供清晰的用户提示和重试入口。
- 后端返回的 Markdown 或富文本内容需要经过安全过滤后再渲染。

### 3.5 前端实施状态

已完成 API 契约确认、React/Vite 工程、认证、聊天流、历史会话、删除、Steam
绑定、主题设置、桌面/移动视觉冒烟和真实后端端到端联调。当前仅剩最终视觉方案
确认，详见 `FRONTEND_DESIGN.md`。

### 3.6 前端验收标准

- 前端各功能能够正确调用对应后端接口。
- 登录过期时页面能正确回到未登录状态。
- 聊天、加载、失败、空数据和流式结束状态清晰可用。
- 用户只能看到和操作自己的会话及数据。
- 页面代码按职责拆分，修改单个功能不会依赖一个超大的 HTML 文件。
- 用户输入和后端内容经过必要的安全处理。

## 4. 当前实施状态

```text
后端接口与数据契约
  -> 后端一致性与安全测试
  -> React/Vite 前端接入
  -> 桌面/移动视觉验收
  -> 真实后端端到端联调
```

本项目不要求先把所有后端接口都做成前端页面。只需要让前端使用当前产品真正需要的接口；运维、测试和后台接口可以独立存在。

## 5. 文档和开发记录方式

本项目采用“分阶段执行、每阶段记录”的方式。已完成工作继续追加记录，不能用
旧阶段计划覆盖当前实现状态。

每次开始新的 AI 工作窗口时，应先读取以下文件：

1. `AGENTS.md`
2. `后端与前端实施技术文档.md`
3. `IMPLEMENTATION_PROGRESS.md`
4. 与当前任务相关的 `API_CONTRACT.md` 或 `FRONTEND_DESIGN.md`

每次完成一项工作后，应更新 `IMPLEMENTATION_PROGRESS.md`，至少记录：

- 本次完成的内容。
- 修改过的文件。
- 已执行的测试及结果。
- 尚未解决的问题。
- 下一步建议。

代码阶段使用 Git 提交保存，进度文档记录具体工作内容，二者共同作为后续继续开发的依据。新的 AI 窗口不得只依赖上一轮聊天记录，应以项目中的文档和代码为准。
