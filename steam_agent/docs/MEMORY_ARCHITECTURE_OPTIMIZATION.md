# Steam Agent 记忆架构优化技术文档

## 1. 文档目的

本文档总结当前项目对话记忆的设计结论，并定义后续待修改的目标架构。

核心目标：

1. 当前会话使用 LangGraph checkpoint 保持上下文。
2. 用户长期偏好、限制和事实使用结构化记忆保存，并在后续会话中注入。
3. 用户明确要求查找历史原文时，直接查询 SQLite。
4. 移除目前不必要的“全部历史对话向量化后再做语义回忆”链路。
5. 保留游戏知识库的 Dense + BM25 + RRF + 重排检索，它与用户对话记忆是两套不同功能。

实现状态：P0、P1 和 P2 已落地。历史 Chroma 用户记忆集合仍保留，仅用于按用户删除线程时的兼容清理；本次没有做全量历史向量迁移或删除。

## 2. 最终结论

本项目不需要把所有历史对话都保存为向量记忆，也不需要为历史对话建立独立的混合检索系统。

推荐采用两类记忆：

```text
当前会话记忆
    LangGraph checkpoint

当前会话摘要
    当前线程的压缩摘要
    SQLite 持久化，并同步保存在 checkpoint 状态中

用户长期记忆
    结构化 memory 记录
    由模型提出 add / replace / delete 操作
    由后端执行，并在新会话初始化时注入

原始历史记录
    SQLite
    按 user_id、thread_id、turn_number、role 精确查询
```

长期记忆的逻辑形式可以称为“memory 文档”，但物理存储建议继续使用结构化数据库记录，而不是让模型直接改写一整篇自由文本。这样更容易实现去重、替换、删除、过期和权限隔离。

## 3. 现有项目评估

### 3.1 已有且应保留的部分

| 现有能力 | 位置 | 判断 |
|---|---|---|
| 当前会话状态保存 | `graph/builder.py`、`checkpoints.db` | 保留 |
| 用户长期偏好存储 | `memory/insight_store.py`、`data.db` | 保留并规范化 |
| 长期记忆注入系统提示词 | `prompts/system.py` | 保留 |
| 精确读取历史消息 | `tools/recall_message_detail.py` | 保留 |
| 用户、线程、轮次、角色字段 | `memory/message_store.py` | 保留 |
| 游戏知识库检索 | `rag/`、`tools/rag_search.py` | 保留，不与用户记忆混合 |

### 3.2 当前存在的重复链路

现在每轮对话会执行以下过程：

```text
用户消息 + AI 回复
    ↓
SQLite 保存原始消息
    ↓
同时生成向量
    ↓
写入 Chroma 用户记忆集合
    ↓
模型以后可以调用 recall_user_memory 做语义检索
```

这会产生两份历史数据：

1. SQLite 中的权威原始对话。
2. Chroma 中的语义副本。

按照本项目目前确定的产品需求，第二份副本没有必要作为日常能力使用，反而增加了：

- 向量模型依赖；
- Chroma 用户记忆集合维护成本；
- 归档失败重试逻辑；
- 数据一致性问题；
- 模型错误回忆历史内容的风险；
- 额外的隐私和删除同步问题。

### 3.3 当前长期记忆能力已经接近目标

`memory/insight_store.py` 已经具备以下字段和机制：

- `user_id`
- `insight`
- `category`
- `normalized_key`
- `confidence`
- `source`
- `scope`
- `expires_at`
- `active`
- `superseded_by`

它已经支持同一主题的去重和旧记录失效。因此后续不是重新设计一套记忆系统，而是把模型输出契约和写入动作进一步明确。

## 4. 目标架构

### 4.1 Agent 主流程

```text
用户请求
    ↓
API 身份校验
    ↓
安全 Guard
    ↓
Agent 模型
    ├─ 需要当前上下文：使用 LangGraph checkpoint
    ├─ 需要长期偏好：使用已注入的结构化记忆
    ├─ 需要保存或修改记忆：调用 save_user_insight
    ├─ 用户明确要求历史原文：调用 recall_message_detail
    └─ 需要游戏数据：调用 Steam / 游戏 RAG 工具
    ↓
答案校验
    ↓
SQLite 保存本轮原始对话
    ↓
返回结果
```

### 4.2 记忆分类

| 类型 | 内容 | 存储 | 读取方式 |
|---|---|---|---|
| 当前会话记忆 | 当前线程中的上下文和工具结果 | LangGraph checkpoint | 自动进入当前 Agent 状态 |
| 长期用户记忆 | 偏好、限制、稳定事实 | SQLite 结构化记录 | 构造系统提示词时注入 |
| 原始历史记录 | 用户和助手的完整消息 | SQLite | `recall_message_detail` 精确查询 |
| 游戏知识库 | 游戏描述、标签、评分等 | Chroma + BM25 索引 | `rag_search_similar_games` |

### 4.3 每次模型调用与缓存

每次模型调用都需要根据当前 checkpoint 状态，逻辑上重新组装完整请求：

```text
固定前缀
    系统提示词
    工具 / Skill 描述
    新会话初始化时注入的长期记忆快照
动态部分
    当前会话摘要
    摘要之后保留的最近完整对话轮次
    当前待处理输入
```

“重新组装请求”不等于“无法复用缓存”。前缀缓存通常要求前缀的序列化结果完全一致，不能只比较 token 数量。只要系统提示词、工具 / Skill 描述和会话级长期记忆快照没有变化，且它们在请求中的顺序和内容一致，就可以复用对应的前缀缓存；变化的摘要和最近对话放在固定前缀之后。

因此，长期记忆在一个会话中采用快照语义：会话开始时读取并注入一次，后续调用复用同一个快照。当前会话中新写入的长期记忆先持久化，但默认在下一次新会话初始化时生效，以保持稳定的缓存前缀。当前用户在本轮明确提出的新要求仍然优先于旧的画像快照。

### 4.4 当前会话的读取边界

正常连续对话时，当前运行中的图状态从 LangGraph checkpoint 恢复，不从保存原始消息的 `messages` 表重新拼装。当前请求内的节点之间直接使用内存中的状态；跨请求或服务重启后，由 `checkpoints.db` 恢复状态。

上下文压缩完成后：

1. 摘要写入 SQLite 的会话摘要表，记录用户、线程、覆盖轮次、版本和更新时间。
2. 摘要同步写入当前图状态并保存到 checkpoint，下一节点直接使用内存状态。
3. 下一次用户请求优先从 checkpoint 读取摘要和最近消息。
4. 只有 checkpoint 缺失、损坏、需要恢复或显式重放时，才从 SQLite 摘要和原始消息重建上下文。

不建议每一轮都从 SQLite 原始消息表重建当前上下文，因为该表不一定包含完整的工具调用、工具结果和图运行状态。

## 5. 长期记忆写入设计

### 5.1 模型输出结构

模型不直接编辑自由文本 memory 文档，而是输出结构化工具参数：

```json
{
  "memory_key": "喜欢的游戏类型",
  "value": "开放世界、探索类",
  "action": "replace",
  "category": "preference",
  "confidence": 0.9,
  "scope": "stable",
  "ttl_days": null
}
```

字段含义：

| 字段 | 说明 |
|---|---|
| `memory_key` | 记忆主题的稳定键，例如“喜欢的游戏类型” |
| `value` | 当前记忆内容 |
| `action` | `add`、`replace` 或 `delete` |
| `category` | `preference`、`constraint` 或 `fact` |
| `confidence` | 模型对该记忆的置信度 |
| `scope` | `stable`、`temporary` 或 `session` |
| `ttl_days` | 临时记忆的有效天数 |

项目现有代码使用 `insight` 表示内容。实现时可以继续使用数据库字段 `insight`，但对模型暴露的工具参数建议使用更直观的 `value`，由工具层完成映射。

### 5.2 动作语义

#### `add`

新增一个主题记忆。如果相同用户、相同主题、相同内容已经存在，则去重，不重复插入。

#### `replace`

用新内容替换同一 `memory_key` 下的有效旧记忆：

1. 新增一条记录。
2. 将旧记录标记为 `active=0`。
3. 通过 `superseded_by` 保留替换关系。

不建议物理删除旧记录，方便审计和排查模型记忆错误。

#### `delete`

按照 `user_id + memory_key` 删除或停用该主题的有效记忆。删除不应该依赖用户重新提供完整的旧句子，否则容易因为文字不同而删除失败。

### 5.3 写入规则

模型负责提出记忆操作，后端负责最终执行和校验。

应该写入长期记忆的内容：

- 用户明确要求“记住”的偏好或事实；
- 稳定的游戏类型偏好；
- 长期预算、平台、设备等限制；
- 用户明确要求以后遵守的规则。

不应该写入长期记忆的内容：

- 一次性的临时需求；
- 当前只针对一款游戏的即时判断；
- 模型自行猜测、用户没有确认的偏好；
- 完整的原始对话文本。

建议规则：

- 用户明确要求记忆时，可以直接写入。
- 模型从上下文推断出的偏好，应降低 `confidence`，必要时先向用户确认。
- `stable` 记忆不设置过期时间。
- `temporary` 和 `session` 记忆必须设置默认过期时间。
- 写入工具必须强制使用当前认证用户的 `user_id`，不能相信模型自行传入的用户 ID。

## 6. 长期记忆注入设计

每个新会话开始时，读取当前用户的有效长期记忆，生成一次会话级快照，并以紧凑形式放入系统提示词：

```text
已确认用户画像：
- [preference] 喜欢开放世界、探索类游戏
- [constraint] 预算通常不超过 100 元
- [fact] 主要使用 PC 平台
```

注入原则：

1. 只注入 `active=1` 且没有过期的记录。
2. 只注入当前用户的记录。
3. 限制条数和总字符数，不能把整份历史记忆无限塞进上下文。
4. 同一个会话内固定使用该快照，不因每一轮重新查询数据库而改变固定前缀。
5. 当前会话中新写入、替换或删除的长期记忆默认在下一次新会话初始化时生效；如产品需要立即生效，必须明确接受前缀缓存失效的代价并重新生成会话前缀。
6. 长期记忆是个性化线索，不应覆盖用户当前明确的新要求。

当前 [`prompts/system.py`](../prompts/system.py) 已经通过 `get_insights(user_id)` 完成了基本注入，后续主要是统一字段和限制注入规模。

### 6.1 长期记忆写入的执行模式

简单场景可以由当前 Agent 模型判断并调用 `save_user_insight`。对于需要批量提取、总结、去重、冲突检查或质量审查的场景，推荐由异步记忆子 Agent 使用专门的总结模型后台处理：

```text
当前会话完成
    ↓
后台子 Agent 读取本轮对话或候选记忆
    ↓
提取、去重、冲突检查、生成结构化操作
    ↓
后端校验并写入 user_insights
    ↓
下一次新会话注入
```

子 Agent 不直接修改 SQLite，也不绕过后端权限校验；它只提出结构化的 `add`、`replace` 或 `delete` 操作。

### 6.2 异步任务、幂等与质量审查

本项目的异步记忆子 Agent 使用 SQLite `memory_tasks` 队列表，不使用进程内队列作为唯一状态：

1. 本轮用户消息、助手回答和 `memory_tasks` 记录在同一个 SQLite 事务中写入；归档失败时不会留下孤立任务。
2. 任务以 `user_id + thread_id + turn_number` 唯一，worker 通过租约领取；进程崩溃或租约过期后可以再次领取。
3. 模型失败使用指数退避重试，超过 `MEMORY_AGENT_MAX_ATTEMPTS` 后标记为 `failed`，不阻塞主聊天响应。
4. 任务重复执行不会产生重复记忆：数据库层通过 `memory_key` 和内容去重，`replace`、`delete` 仍由 `save_insight` 的后端校验执行。
5. 写入前必须满足明确的记忆意图、允许的枚举字段、置信度阈值，以及 `evidence` 必须是用户原话连续片段；助手回答不能作为记忆证据。
6. 会话删除时同步删除该线程的未完成任务，worker 只通过记忆存储服务写入，不直接修改 SQLite 表。

默认 worker 在 API 进程启动时运行，也会在启动时先领取遗留任务。可以用 `MEMORY_AGENT_ENABLED=false` 暂停领取，任务会保留在 SQLite 中等待后续恢复。

## 7. 上下文压缩设计

### 7.1 Hermes 风格的压缩边界

上下文压缩只作用于固定前缀之后的动态对话区，不修改以下内容：

- 系统提示词；
- 工具和 Skill 描述；
- 新会话初始化时注入的长期记忆快照。

推荐的动态上下文结构为：

```text
固定前缀
    系统提示词 + 工具 / Skill 描述 + 长期记忆快照
动态上下文
    历史摘要（如果存在）
    最近若干个完整对话轮次
    当前用户输入
```

### 7.2 触发条件

压缩的主要触发依据是 token 预算，而不是对话轮数。建议根据模型上下文窗口计算：

```text
动态历史预算 = 模型上下文上限
             - 固定前缀 token
             - 预留的模型输出 token
             - 预留的工具调用和结果 token
```

当动态历史达到该预算的约 90% 时触发压缩。90% 是默认阈值，应配置化；如果工具结果或模型输出波动较大，可以提前到 80%～85%。压缩必须以完整对话轮次为边界，不能截断工具调用和工具结果的配对关系。

### 7.3 摘要持久化与继续运行

上下文压缩位于当前请求的主链路上：如果当前请求还需要继续调用模型或工具，摘要必须在下一次模型调用前同步生成。可以使用专门的总结模型，但不能把这一步完全放到异步后台。异步子 Agent 适合处理跨请求的长期记忆提取和整理。

压缩模型生成的摘要保存到 SQLite 的独立会话摘要表，并关联以下元数据：

- `user_id`；
- `thread_id`；
- 摘要版本；
- 摘要覆盖的起始和结束轮次；
- 摘要正文；
- 创建和更新时间。

当前请求未中断时，压缩后的摘要同时写入内存中的图状态，并随 checkpoint 保存；下一节点和下一轮请求直接使用该状态。服务重启或 checkpoint 不可用时，再依据摘要元数据从 SQLite 恢复，不需要每轮都从 SQLite 重建。

压缩后下一轮仍然会重新组装请求，但只是把旧的动态历史替换为摘要和最近对话；固定前缀保持不变，因此固定前缀的缓存仍可复用。

## 8. 原始历史精确查询

### 8.1 保留的工具

保留：

```text
recall_message_detail
```

它应该按照以下字段查询 SQLite：

- 当前认证用户 `user_id`；
- `thread_id`；
- 可选的 `turn_number`；
- 可选的 `role`。

### 8.2 适用问题

- “把上一次对话原文找出来。”
- “我在第 3 轮说了什么？”
- “找出这个线程里我说过的话。”
- “你之前对这个游戏是怎么评价的？”

### 8.3 安全要求

模型不应决定要查询哪个用户。`user_id` 必须由服务端从认证身份注入。

`thread_id` 必须经过当前用户范围校验，不能通过传入其他用户的线程 ID 读取数据。

## 9. 删除或停用的历史语义记忆链路

### 9.1 从 Agent 工具中移除

从 [`graph/nodes.py`](../graph/nodes.py) 的工具注册中移除：

```text
recall_user_memory
```

后续模型不再拥有“对全部历史对话做向量回忆”的工具。

### 9.2 停止原始对话写入用户向量库

调整 [`memory/archiver.py`](../memory/archiver.py)：

1. 对话原文只保存到 SQLite。
2. 不再把每轮 `User + Assistant` 文本嵌入 Chroma 用户记忆集合。
3. 移除或废弃面向语义归档失败的重试逻辑。
4. 保留 SQLite 写入失败的错误处理和指标记录。

现有 Chroma 游戏集合不受影响。游戏推荐仍然可以继续使用 Dense、BM25、RRF 和 CrossEncoder 重排。

### 9.3 兼容和迁移

不建议在第一次修改时直接删除历史 Chroma 用户记忆数据。建议分阶段：

1. 已停止新数据写入。
2. 已从 Agent 工具列表中移除 `recall_user_memory`。
3. 观察一段时间确认没有业务依赖。
4. 再移除用户记忆向量集合、记忆 embedding 配置和相关代码。

游戏知识库使用的向量模型、集合和重排配置继续保留。

## 11. 验收标准

### 长期记忆

- 用户明确说“记住我喜欢开放世界游戏”后，产生结构化 `add` 操作。
- 用户说“我现在不喜欢开放世界了”后，旧记录失效，新记录生效。
- 用户要求忘记该偏好后，按照 `memory_key` 停用对应记录。
- 同样的记忆重复写入不会产生无意义重复记录。
- 新会话可以看到有效长期记忆。
- 过期的临时记忆不会被注入。
- 同一会话内写入的新长期记忆默认不改变已建立的固定前缀；下一次新会话可以看到更新后的快照。

### 上下文与缓存

- 每次模型调用都能从当前 checkpoint 状态重新组装请求。
- 固定前缀内容和顺序不变时，能够保持前缀 token 序列一致并具备缓存命中条件。
- 只改变摘要或最近对话时，不会重新生成系统提示词、工具 / Skill 描述和长期记忆快照。
- 动态历史达到配置阈值时触发摘要；默认阈值约为动态预算的 90%。
- 压缩不会修改固定前缀，也不会截断不完整的工具调用链。
- 压缩摘要同时存在于 SQLite 和 checkpoint；当前请求的下一节点直接使用 checkpoint 状态。
- 服务重启后可以从 checkpoint 恢复摘要；checkpoint 缺失时可以从 SQLite 摘要和原始消息恢复。
- 原始历史仍可通过 SQLite 按线程和轮次查询。

### 原始历史

- 指定 `thread_id` 能返回正确历史消息。
- 指定 `turn_number` 能返回正确轮次。
- 指定 `role=user` 或 `role=assistant` 能正确过滤。
- 用户不能读取其他用户的消息。
- 查询原文不依赖 embedding 模型或 Chroma 服务。

### 工具和依赖

- Agent 工具列表中不再暴露 `recall_user_memory`。
- 普通聊天不会触发历史对话向量检索。
- 游戏推荐的 RAG 流程不受影响。
- Chroma 暂时不可用时，长期记忆和精确历史查询仍然可用。
- 记忆子 Agent 异步失败时不阻塞主回答，任务可重试且重复执行不会产生重复记忆。

## 12. 不在本次优化范围内的内容

- 不修改游戏知识库的 Dense + BM25 + RRF + CrossEncoder 流程。
- 不新增跨所有历史对话的语义总结功能。
- 不新增历史推荐结果专用向量索引。
- 不把当前会话上下文复制进长期记忆。
- 不让模型直接改写 SQLite 或任意本地文件。

## 13. 最终架构一句话

> LangGraph checkpoint 负责当前会话状态，SQLite 持久化会话摘要和原始历史，结构化长期记忆在新会话初始化时形成稳定快照，Chroma 只服务于游戏知识库；动态历史按 token 阈值压缩，但不修改固定前缀。
